# 01 · 点击「不认识」的完整旅程

这是整套文档里最重要的一篇。看完它，你应该能回答：

> 我点一下「不认识」，**到底发生了什么？数据去了哪里？页面为什么知道该显示下一个词？**

我们跟着一次真实点击，从浏览器一路走到数据库，再走回来。

---

## 先约定一个场景

假设你打开 `/study`，屏幕上显示第一个单词：

```
┌──────────────────────────┐
│          [新词]           │
│                          │
│        abandon           │
│      /əˈbændən/          │
│          vt.             │
│                          │
│    ┌──────────────┐      │
│    │  显示释义     │      │
│    └──────────────┘      │
└──────────────────────────┘
        第 1 / 32 个
```

数据库里：
- `words` 表有 `id = 1, word = 'abandon'`
- `user_word_progress` 表**没有**这个词的记录（第一次学）
- 你的用户 ID 是 `user_id = '1111...'`

下面开始。

---

## 第 0 步：你还没点击之前，页面是怎么来的

这一步很重要，因为**你点按钮时用到的东西，有一部分是这一步就准备好的**。

```
① 浏览器地址栏输入 localhost:3000/study
        ↓
② proxy.ts（项目根目录）先拦一道
   → lib/supabase/proxy.ts 里的 updateSession()
   → 刷新登录令牌；没登录就跳去 /login
        ↓
③ 进入 app/study/page.tsx（这是「服务端组件」，在服务器上跑）
   第 34 行  const user = await requireUser();
            → 向 Supabase Auth 问「现在登录的是谁」
   第 42 行  const queue = await getStudyQueue(user.id);
            → 去数据库取今天该背的词（见下面拆解）
        ↓
④ getStudyQueue 内部（lib/progress.ts）做了四件事：
   a. getDueEntries      取 next_review_time 已到期的旧词
   b. countNewWordsAvailable  数一下还剩多少词没学过
   c. buildDailyPlan     算出"今天复习几个 + 学几个新词"
   d. getNewEntries      调数据库函数 get_new_words 取新词
        ↓
⑤ 回到 page.tsx 第 114 行：
   <StudySession items={items} onRate={submitReview} />
        ↓
⑥ StudySession 是「客户端组件」，但它在服务器上先渲染出一份 HTML
   （此时是初始状态：第 1 个词，释义隐藏）
        ↓
⑦ 服务器把两样东西一起发给浏览器：
   - 渲染好的 HTML（你马上能看见内容）
   - items 这份数据 + onRate 的"调用凭证"（不是一个真函数，
     而是一个"能联系上服务器"的引用）
        ↓
⑧ 浏览器显示 HTML —— 你已经能看到 abandon 了
   但此时按钮还点不动，因为 JS 还在下载
        ↓
⑨ JS 加载完成，React 接管页面（这叫 hydration「注水」）：
   把 onRate 还原成"点了能调用服务器的函数"
        ↓
⑩ 现在可以点击了 ✅
```

**第 ⑦ 步值得多看一眼。** 为什么能传 `onRate={submitReview}` 这个函数？

因为它是 Server Action。服务端组件**不能**把普通函数传给客户端组件（函数没法被序列化，
没法通过网络传）。但 Server Action 不一样：Next.js 会给它生成一个编号，
浏览器这边拿到的是一个"帮我调用编号 X 的那个服务器函数"的替身。
所以你传的其实不是函数本身，而是一张"取货单"。

## 第 1 步：点「显示释义」——这一步**没有**网络请求

你点「显示释义」：

```
components/WordCard.tsx 的按钮 onClick
        ↓
components/StudySession.tsx 里：
   onReveal={() => setRevealed(true)}
        ↓
React 把 revealed 从 false 改成 true
        ↓
重新渲染 → 释义和例句出现，「显示释义」按钮消失
```

**关键认知：这一步完全在你自己的浏览器里完成，没有任何数据发到服务器。**

这也是为什么它快得没有延迟感。`revealed` 叫"本地状态"——它只影响"显示什么"，
不需要保存到任何地方。就算你刷新页面，它变回隐藏状态，也无所谓。

## 第 2 步：点「不认识」——真正的旅程开始

### 2.1 浏览器里发生的事

```
components/RatingButtons.tsx:64
   onClick={() => onRate(button.rating)}
        ↓  onRate 是 StudySession 通过 props 传进来的
components/StudySession.tsx:271
   onRate={(rating) => void handleRate(rating)}
        ↓
components/StudySession.tsx:187
   async function handleRate(rating: ReviewRating) {
```

进入 `handleRate` 之后，做了**两件事**，顺序很重要：

```ts
// ① 先在本地用同一个算法算一遍（第 190~192 行）
const now = new Date();
const before = progressMap[currentItem.word.id];      // 当前进度
const after = scheduleNextReview(before, rating, now); // 算出来是 "10 分钟后"

// ② 然后才请求服务器保存（第 198 行）
const result = await onRate(currentItem.word.id, rating);
```

**为什么要在本地先算一遍？** 因为按钮下面那行小字（"10 分钟后"）需要立刻更新，
不能等服务器回复。而且算法是纯函数，本地算和服务器算结果一定相同 —— 这是前面
写测试保证过的。

### 2.2 参数是怎么传出去的

`onRate(currentItem.word.id, rating)` 这两个参数：

| 参数 | 值 | 从哪来 |
| --- | --- | --- |
| `wordId` | `1` | 来自第 0 步服务器发来的 `items` 数据里的 `word.id` |
| `rating` | `"again"` | 就是你点的是哪个按钮，写死在 `RatingButtons.tsx` 的配置里 |

⚠️ **注意这里没有 `user_id`。** 这是有意的 —— 见下一步。

### 2.3 从浏览器到服务器

浏览器把这次调用打包成**一个 POST 请求**发出去：

```
POST /study
{
  "action": "submitReview",     ← 哪个 Server Action
  "args": [1, "again"]          ← 两个参数
}
Cookie: sb-xxxx-auth-token=...  ← 登录凭证（浏览器自动带上）
```

## 第 3 步：服务器收到请求，先确认「你是谁」

```
app/study/actions.ts:25
   export async function submitReview(wordId, rating) {
```

它做的第一件事是**校验参数**：

```ts
if (!Number.isInteger(wordId) || wordId <= 0) {
  return { ok: false, error: "单词编号不合法。" };
}
if (!VALID_RATINGS.includes(rating)) {
  return { ok: false, error: "作答类型不合法。" };
}
```

**为什么界面明明只有三个按钮，还要检查？**

因为 Server Action 本质上是一个**公开的网络接口**。界面上只有三个按钮，
但任何人都可以用工具（比如 Postman）直接向它发请求，传任意参数进来。

界面上的限制 ≠ 接口的限制。所以每个入口都必须自己检查。

然后它调用真正的保存函数（`actions.ts:37`）：

```ts
await saveReview(wordId, rating);
```

## 第 4 步：服务端确认身份 —— 你问的「获取 user_id」在这里

进入 `lib/progress.ts:194`：

```ts
export async function saveReview(wordId: number, rating: ReviewRating) {
  const supabase = await createClient();
  const userId = await requireCurrentUserId(supabase);   // ← 第 199 行
```

`requireCurrentUserId`（`lib/progress.ts:57`）内部：

```ts
const { data, error } = await supabase.auth.getUser();
if (error !== null || data.user === null) {
  throw new Error("登录状态已失效，请重新登录。");
}
return data.user.id;
```

### 这里是最关键的安全设计

`user_id` **不是从前端传进来的**，而是服务器自己向 Supabase Auth 问出来的：

```
服务器 → Supabase Auth：这个 cookie 里的令牌是谁的？
Supabase Auth → 服务器：是 1111... 的（令牌签名验证通过）
```

**为什么不信任前端传的 `user_id`？**

因为浏览器里的一切都能被改。用户可以打开开发者工具，把请求里的 `user_id`
改成别人的。但如果服务器不接收这个参数、自己去问，那前端改什么都白搭。

> 💡 记住这句话：**"前端传来的东西一律不可信，能自己查就自己查。"**

## 第 5 步：读出这个词现在的进度

`lib/progress.ts` 第 203~210 行附近：

```ts
const { data: existing } = await supabase
  .from("user_word_progress")
  .select("familiarity, consecutive_correct, review_count, correct_count, wrong_count")
  .eq("user_id", userId)
  .eq("word_id", wordId)
  .maybeSingle();

const current: ReviewInput = existing ?? createInitialProgress();
```

因为 `abandon` 是第一次学，数据库里没有记录 → `existing` 是 `null`
→ 用 `createInitialProgress()` 得到全 0 的初始进度：

```
familiarity: 0, consecutive_correct: 0,
review_count: 0, correct_count: 0, wrong_count: 0
```

> `maybeSingle()` 的意思是"最多一条，没有就返回 null"。
> 用 `single()` 的话，查不到会直接报错。

## 第 6 步：算法决定下次什么时候复习

`lib/progress.ts:218`：

```ts
const next = scheduleNextReview(current, rating, new Date());
```

进入 `lib/spaced-repetition.ts:81`。因为你点的是 `"again"`，走第 94 行那个分支：

```ts
if (rating === "again") {
  return {
    ...base,                        // review_count + 1、last_review_time = 现在
    familiarity: 0,                 // 掌握程度 → 不认识
    consecutive_correct: 0,         // 连击清零
    wrong_count: base.wrong_count + 1,   // 答错次数 +1
    next_review_time: new Date(
      now.getTime() + AGAIN_INTERVAL_MINUTES * MINUTE_MS,   // 现在 + 10 分钟
    ).toISOString(),
  };
}
```

算出来的结果：

| 字段 | 原来 | 现在 |
| --- | --- | --- |
| `familiarity` | 0 | **0**（本来就不认识） |
| `consecutive_correct` | 0 | **0** |
| `review_count` | 0 | **1** |
| `correct_count` | 0 | 0 |
| `wrong_count` | 0 | **1** |
| `last_review_time` | null | **现在** |
| `next_review_time` | null | **现在 + 10 分钟** |

> 如果点的是「认识」，会走第 113 行之后的逻辑，`next_review_time` 变成
> 3 天后，且 `consecutive_correct` 变成 1。这就是"3→7→14→30"阶梯的起点。

**这个函数是纯函数**：给它同样的输入，永远得到同样的输出，不碰数据库、
不看系统时间（`now` 是参数传进来的）。所以它能被 46 个自动化测试死死钉住。

## 第 7 步：写回数据库 —— 这里发生了一次「RLS 检查」

`lib/progress.ts:225`：

```ts
const { error: writeError } = await supabase
  .from("user_word_progress")
  .upsert(
    { user_id: userId, word_id: wordId, ...next },
    { onConflict: "user_id,word_id" },
  );
```

这次请求带着你的登录 cookie 发出，Supabase 那边会做**两次检查**：

### 检查一：upsert 怎么知道是"更新"还是"插入"？

靠建表时写的这一行约束（`supabase/schema.sql:113`）：

```sql
unique (user_id, word_id)
```

"一个用户对一个词只能有一条记录"。所以 `onConflict: "user_id,word_id"` 是在告诉
数据库：**如果已经存在同一个 (我, 这个词) 的记录，就更新它，不要再插一条。**

没有这个约束，upsert 就没法工作 —— 数据库不知道该按什么判断"重复"。

### 检查二：RLS —— 数据库自己再确认一遍身份

因为 `user_word_progress` 表开了行级安全（`schema.sql:138`），
写入时必须通过这条策略（`schema.sql:155`）：

```sql
create policy "进度：只能插入自己的"
  on public.user_word_progress
  for insert
  to authenticated
  with check ((select auth.uid()) = user_id);
--                                  ↑ 数据库自己算出的"你是谁"
--                                              ↑ 你要写入的 user_id
```

`auth.uid()` 是 Supabase 从请求的登录令牌里解出来的，**前端无法伪造**。

**所以就算第 4 步哪天被写错了**（比如不小心改成接收前端传来的 user_id），
只要写入的 `user_id` 和令牌里的对不上，数据库还是会拒绝。

> 这叫**纵深防御**：不把安全押在单一一处。
> 这套策略我用 PGlite（本地跑的真实 PostgreSQL）实测过 33 个用例，
> 包括"A 显式写 `where user_id = B的ID` 也只会拿到 0 行"。

写入成功后，`user_word_progress` 表里就有了：

```
id | user_id | word_id | familiarity | consecutive_correct | review_count | wrong_count | next_review_time
 1 | 1111... |    1    |      0      |          0          |      1       |      1      | 2026-10-12 20:20:00
```

> 顺带一提：`updated_at` 是数据库的**触发器**自动填的，
> 不需要代码去管（`schema.sql` 里的 `set_progress_updated_at`）。

## 第 8 步：记一笔流水

`lib/progress.ts:236`：

```ts
const { error: logError } = await supabase.from("review_logs").insert({
  user_id: userId,
  word_id: wordId,
  rating,                              // "again"
  familiarity_after: next.familiarity, // 0
});

if (logError !== null) {
  console.error("写入学习流水失败（不影响背单词）：", logError.message);
}
```

**注意这里是 `console.error`，而不是 `throw`。** 这是刻意的：

| 哪一步失败 | 后果 | 处理方式 |
| --- | --- | --- |
| 进度写入失败 | 你以为背过了，其实没保存 | **必须报错**，停在这个词不让往下走 |
| 流水写入失败 | 统计图表少一笔 | **只记日志**，继续背 |

为什么流水失败不能报错？因为进度**已经存进去了**。如果这时报错，页面会显示
"保存失败"并停住，你再点一次 —— **进度会被再写一遍，复习次数翻倍**。
那比丢一条统计记录糟糕得多。

## 第 9 步：返回结果

回到 `app/study/actions.ts`：

```ts
await saveReview(wordId, rating);   // 第 37 行
revalidatePath("/");                // 第 40 行
return { ok: true };                // 第 42 行
```

**`revalidatePath("/")` 是干什么的？** 它告诉 Next.js："首页缓存的统计数字作废了，
下次有人访问重新算。" 不做这一步，你背完词回首页，可能还看到旧数字。

> **为什么用返回值 `{ ok: false, error }` 而不是抛异常？**
> 因为错误信息要跨网络传回浏览器。抛出的异常经过这一趟，细节常常丢失，
> 前端只能看到笼统的"服务器错误"。把结果当普通数据传回来，
> 就能把"登录过期了""数据库表还没建"这类具体原因原样显示给你。

## 如果失败了会怎样

这是设计里很重要的一部分。假设第 7 步写入失败（比如网络断了）：

```
saveReview 抛出异常
   ↓
actions.ts 的 try/catch 接住 → return { ok: false, error: "保存学习进度失败：..." }
   ↓
StudySession.tsx 收到 result.ok === false
   ↓
setError(result.error)
setIsSaving(false)
return;              ← 注意这个 return
   ↓
★ 页面停在这个单词不动，显示红色错误提示
```

**为什么坚持"失败就不前进"？**

如果失败了还往下走，你会以为这个词背过了、进度也记上了。**但实际上没有。**
等你明天回来，这个词还在"新词"里，你会困惑"我昨天不是背过了吗"。

宁可当场报错让你重试，也不要制造"以为记上了"的假象。

## 五个问题速答

| 问题 | 答案 |
| --- | --- |
| **数据从哪来？** | 单词来自数据库 `words` 表；你的进度来自 `user_word_progress` 表。都是第 0 步服务器提前取好、随页面一起发过来的。 |
| **数据经过什么代码？** | `RatingButtons` → `StudySession.handleRate` → `actions.ts:submitReview` → `progress.ts:saveReview` → `spaced-repetition.ts:scheduleNextReview`。 |
| **最终保存在哪？** | Supabase 的 `user_word_progress` 表（当前进度）+ `review_logs` 表（流水）。都是云端，所以换设备也在。 |
| **页面为什么能显示？** | 服务器先把 HTML 渲染好发过来（所以你立刻能看到内容），然后浏览器加载 JS、React 接管页面（所以按钮能点）。详见 [02](02-页面是怎么显示出来的.md)。 |
| **点按钮后发生了什么？** | 就是上面这 10 步。核心是：本地先算一遍用于即时反馈 → 请求服务器 → 服务器自己确认身份 → 算法算新进度 → 写数据库（数据库再做一次 RLS 检查）→ 返回 → 本地切换下一个词。 |

## 想自己动手验证这条链路？

代码里已经有几处可以观察的地方：

1. **看服务器日志**：`npm run dev` 那个窗口会打印每次请求。
   点一次「不认识」，你会看到 `POST /study` 的记录。
2. **看数据库**：配好 Supabase 后，在控制台的 Table Editor 里打开
   `user_word_progress` 表，背几个词，刷新 —— 能看到行数和
   `next_review_time` 在变。
3. **故意制造失败**：把 `.env.local` 里的密钥改错一个字符，重启，点按钮 ——
   你会看到错误提示，而且**页面停住不前进**。这就是上面说的"失败不前进"。
