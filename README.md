# 考研英语背单词

一个为自己长期使用的个性化考研英语背单词网站。目标：每天能真正用起来，学习进度永久保存在云端，换电脑、换手机、退出登录都不会丢。

> 面向 2027 年 12 月考研。英语是薄弱科目，所以这个项目的重点是**长期坚持**和**复习安排**，不是花哨的界面。

## 🌐 在线使用

# **https://kaoyan-words.vercel.app**

手机、平板、公司电脑 —— 任何设备打开都能用，进度自动同步到云端。

> 分享/菜单 → 添加到主屏幕。之后点图标就像打开一个 App，背单词不用再输网址。

### 关于本机的网络代理

这台电脑通过 `127.0.0.1:7897` 上的代理上网。但 **Node.js 默认不读 Windows 的系统代理设置**，
直连 Supabase 会被重置，页面报 `TypeError: fetch failed`。

所以 `npm run dev` 走的不是 `next dev`，而是包装脚本 `scripts/dev.mjs`：
它先读 `.env.local` 里的 `HTTPS_PROXY`，把代理设置正确传进环境变量，再启动 Next.js。

> **如果哪天代理软件换了端口**：改 `.env.local` 里 `HTTPS_PROXY` 那一行即可。
> 想跳过包装直接启动（排查问题时），用 `npm run dev:direct`。

部署到 Vercel 后完全用不到这段逻辑（那边没有代理，直接连）。

导入自己的词库（几千个词也可以）：

```bash
npm run import:words -- data/kaoyan-5000.csv
```

## 每天怎么用

### 启动

打开终端，在项目目录下运行：

```bash
npm run dev
```

看到 `Ready` 之后，浏览器打开 **http://localhost:3000**。用完在终端按 `Ctrl + C` 停止。

> 💡 不需要每次重新 `npm install`，也不需要重建数据库。
> 数据存在 Supabase 云端，关掉浏览器、关掉电脑，下次打开都还在。

### 每天的学习流程

1. **打开首页**，先看几个数字：
   - **今日待复习** —— 到期的旧词，会优先排在前面
   - **今日新词** —— 今天该学几个新词。**这不是硬性指标**，
     是系统照你最近两周的实际节奏算出来的（见下面「学习节奏」一节）
   - **已掌握 / 学习总词数** —— 进度概览
   - **连续学习天数** —— 保持连击的动力
   - **按你最近两周的节奏估算** —— 预计什么时候能背完、考试前来不来得及
2. 点 **「开始学习」**
3. 屏幕上出现一个单词，**先自己在心里想它的意思**，再点「显示释义」对答案
4. 根据刚才想得对不对，点下面三个按钮之一

### 键盘操作（推荐）

手不用离开键盘，长时间背更省力：

| 按键 | 作用 |
| --- | --- |
| `空格` | 显示释义 |
| `1` | 不认识 |
| `2` | 模糊 |
| `3` | 认识 |

### 学习节奏：不要求你每天背多少，而是看你背得动多少

**系统不会规定「每天必须背 20 个」。** 它做的是：

1. 观察你**最近 14 天**每天真正新学了多少词（按 `user_word_progress`
   里每行的 `created_at` 统计 —— 每多一行就是你第一次学了一个新词）
2. 算出平均每天多少个（**休息日也算进去**，这才是可持续的真实节奏）
3. 用它推算：还剩多少词 ÷ 平均节奏 = **预计哪天背完**
4. 对照 **2028 考研初试日期**告诉你来不来得及；来不及就给出每天需要多少

今天安排多少个新词，就是照这个平均节奏来的（限制在每天 5～60 个之间：
低于 5 会停滞，高于 60 容易让你第二天不想打开）。**你背得少它不逼你，
背得多它也不拖后腿 —— 多背几天，预估会自动更新。**

> 估算规则在 `lib/pace.ts`（17 个测试盯着）。
> 考试日期是文件顶部的 `EXAM_DATE_ISO`，**想改直接改那一行**。

### 背词周报（每周末发到邮箱）

**周末你打开网站时**，系统会把这周的情况整理成一封邮件发到你的注册邮箱：

- 本周学了几天、作答多少次、新学多少个词
- 每天的学习量（纯文本柱状图，任何邮箱都不会显示错乱）
- 总进度、连续学习天数
- 本周最该盯的几个词（带星级和错误次数）
- 按最近节奏预计什么时候背完、考试前来不来得及

**一周只发一封** —— 靠数据库的唯一约束保证，所以同时打开几个标签页也不会收到好几封。

> ⚠️ **需要你先做两件事才能收到邮件**（这两步我替你做不了）：
>
> 1. **建表**：去 Supabase → SQL Editor，运行 `supabase/add-weekly-report-log.sql`
>    （只新增一张表，不动已有的 words / user_word_progress / review_logs）
> 2. **配邮件服务**：注册 [Resend](https://resend.com)（免费，3000 封/月），
>    拿到 API Key 后加到 Vercel 的环境变量：名字 `RESEND_API_KEY`
>
> 没配之前**不会报错，只是不发** —— 周报内容照常生成，配好后下个周末就能收到。

**为什么必须接第三方邮件服务**：Supabase 自带的邮件只能发验证码和登录链接，
内容改不了；Vercel 根本没有发邮件的功能。

**为什么不用定时任务**：定时任务跑起来时没有你的登录态，按 RLS 规则读不到你的数据，
除非用 `service_role` 密钥（能绕过所有安全策略，属于高危密钥）。
放在「打开网站时发」既安全又不用配定时任务，代价是周末不打开网站的话邮件会顺延。

代码在 `lib/weekly-report.ts`（内容生成 + 发送时机，27 个测试）、
`lib/email.ts`（实际发送）、`lib/weekly-report-send.ts`（编排 + 防重复）。

### 晚间提醒（晚上 10 点还没开始学就发邮件）

**和周末周报最大的区别：这个必须用定时任务。**
周报可以等你下次打开网站时补发；但「晚上 10 点还没开始」这个条件，
如果你没打开网站恰恰是最需要提醒的时候，所以绕不开定时任务。

#### 发送条件（三个全满足才发）

| 条件 | 说明 |
| --- | --- |
| 今天还没发过提醒 | 定时任务重试也不会发第二封 |
| 今天**一次都没作答** | 只要开始背了就不打扰 —— 这是「没开始」提醒，不是「没背够」提醒 |
| 已经过了 22:00 | 防止手动调用把邮件提前发出去 |

邮件里只有三行数字和一个链接（`待复习 / 新词 / 连续学习`），
不写鼓励也不说教 —— 测试里直接禁止了「加油 / 坚持 / 别放弃 / 记得 / 哦 / 吧」这些词。

#### 为什么它需要 secret key

定时任务跑起来时**没有用户登录态**，按 RLS 规则读不到任何数据，
所以用了 Supabase 的 **secret key**（能绕过所有安全策略）。
这是本项目**唯一**一处绕过 RLS 的地方，限制得很死：

- 环境变量 `SUPABASE_SECRET_KEY` **不带** `NEXT_PUBLIC_` 前缀 → 只存在服务器端
- 只在 `lib/supabase/admin.ts` 里创建，只允许服务端代码 import
- 接口自己校验 `CRON_SECRET`，否则任何人都能调它往你邮箱灌邮件
- 中间件放行 `/api/cron`（否则定时任务会被重定向到登录页，**而且不报任何错**）

#### 配置（需要手动做一次）

| 环境变量 | 从哪来 |
| --- | --- |
| `SUPABASE_SECRET_KEY` | Supabase → Settings → API Keys → Secret keys |
| `CRON_SECRET` | 自己随便生成一串随机字符（48 位左右） |
| `RESEND_API_KEY` | Resend → API Keys |

还要在 Supabase 执行一次 `supabase/add-study-reminder-log.sql`（建发送记录表），
然后 **Redeploy**（环境变量是部署时注入的）。

**调度**：`vercel.json` 里的 `crons` → `0 14 * * *`，即 14:00 UTC = **北京时间 22:00**。
Vercel 免费版触发时间可能在指定小时内浮动，所以实际可能落在 22:00～23:00。

#### 手动测试

```bash
curl -H "Authorization: Bearer $CRON_SECRET" \
  "https://kaoyan-words.vercel.app/api/cron/study-reminder?force=1"
```

带 `?force=1` 会跳过三个判断直接发一封（主题加 `[测试]` 前缀、不写发送记录），
所以不用等到晚上 10 点就能验证链路。不带 `force` 时走真实逻辑。

代码在 `lib/study-reminder.ts`（判断 + 邮件内容，19 个测试）、
`lib/supabase/admin.ts`（管理员客户端）、
`app/api/cron/study-reminder/route.ts`（编排 + 防重复）。

### 每天大概花多久

看你的节奏：平均每天 20 个新词的话，熟练后**大约 15～25 分钟**。

节奏会变：前期新词多、复习少，比较快；往后复习队列变长，时间会稳定在一个区间。
**这是正常的**，间隔复习本来就是这样 —— 越熟的词露面越少。

### 背完之后

首页会显示「今天已经学完啦」。**不需要额外操作** —— 每个词的复习时间已经排好了，
明天打开时，到期的词会自动出现在「今日待复习」里。

### 想换成完整的考研词库

现在装的是 40 个测试单词。换成几千词的正经词库：

```bash
npm run import:words -- data/你的词库.csv
```

然后把生成的 `supabase/seed.sql` 粘贴到 Supabase 的 SQL Editor 里执行。
CSV 的列顺序照着 `data/words-seed.csv` 第一行写就行，脚本会逐行校验并报出问题行号。


**分工原则**：`app/` 只管「页面长什么样」，`lib/` 只管「数据和规则怎么处理」。这样以后改复习算法只需要动 `lib/spaced-repetition.ts`，不用碰页面代码。

`types/database.ts` 值得单独说一句：它把三张表的字段告诉了 TypeScript，
于是**列名写错、表名写错、关联查询名写错、参数名写错都会在编译时报错**，
而不是等到运行时页面崩掉。改完代码跑一次 `npx tsc --noEmit` 就能发现。
（正式项目里这个文件可以用 `npx supabase gen types typescript` 自动生成。）

## 数据库配置（一次性）

1. 在 supabase.com 免费创建项目
2. 把 Project URL 和 Publishable key 填进 `.env.local`（参考 `.env.example`）
3. 打开 Supabase 控制台 → SQL Editor，粘贴执行 `supabase/schema.sql`
4. 再粘贴执行 `supabase/seed.sql`（导入 40 个测试单词）
5. 重启 `npm run dev`，访问 `/diagnostics` 应显示绿色「连接成功」

## 三张表

| 表 | 存什么 | 谁能读 | 谁能写 |
| --- | --- | --- | --- |
| `words` | 单词库（公共数据） | 所有人（含未登录） | 谁都不能，只能在控制台改 |
| `user_word_progress` | 你对每个词的当前进度 | 只有你自己 | 只有你自己 |
| `review_logs` | 每一次作答的流水 | 只有你自己 | 只能追加，不能改也不能删 |

`review_logs` 存在的理由：`user_word_progress` 里只有 `last_review_time`，
它记录的是**最近一次**复习时间。如果你周一背了一次、周三又背一次，周一那次
就被覆盖了，Dashboard 上「最近 7 天每天学了多少」就算不准。流水表则一笔一笔记下来，
同时也为将来的 AI 功能（错词测试、薄弱词总结）准备了历史数据。

## 安全策略已经过实测验证

「用户 A 绝对看不到用户 B 的数据」这条规则，**不是靠前端代码自觉，而是在数据库层强制的**。
而且它已经被真跑过一遍：`supabase/schema.test.ts` 会在本地用 PGlite
（编译成 WebAssembly 的真实 PostgreSQL）起一个临时数据库，先跑
`supabase-shim.sql`（Supabase 环境替身），再把真正的 `supabase/schema.sql`
原封不动执行，然后扮演 A、B、未登录访客三种身份反复试探。

```bash
npm test
```

覆盖的关键场景：

- A 查自己的进度只有 1 条；B 也是 1 条，互相看不到
- A 就算显式写 `where user_id = B的ID`，也只会拿到 0 行
- A 不能把进度写到 B 名下（`with check` 拦截）
- A 改不动、删不掉 B 的记录（受影响行数为 0）
- 未登录访客连进度表都没有访问权限
- 谁都不能往单词库插数据，也不能 `truncate` 清空它（TRUNCATE 不看 RLS，权限单独收回了）
- 流水记录只能追加，改不了也删不掉

## 常见问题

**注册后一直收不到验证邮件？**
Supabase 免费版自带的邮件服务每小时只能发几封。个人自用最省事的做法是关掉邮箱验证：
控制台 → Authentication → Sign In / Providers → Email → 关闭 `Confirm email`。
这样注册后直接就是登录状态。

**登录状态会莫名其妙丢失？**
先确认你的会话刷新文件叫 `proxy.ts` 而不是 `middleware.ts`。Next.js 16 把
middleware 改名成了 proxy，网上大部分 Supabase 教程还是旧写法，照抄会导致
这段代码根本不执行。

**背单词时释义能不能真的藏住？**
视觉上可以，但数据本身会随页面一起发给浏览器（所有客户端渲染的应用都这样，
Anki、欧路词典也一样）。想彻底藏住，得改成「点显示释义时才向服务器要答案」，
那要多一次网络往返，对自用没有必要。

## 艾宾浩斯复习规则

全站按**艾宾浩斯遗忘曲线**安排复习：同一个词会在不断拉长的间隔里反复出现，
每次答对就把间隔推长一档，答错就退回来。

### 复习阶梯（答对时依次往上走）

| 第几次答对 | 下次什么时候见 | |
| --- | --- | --- |
| 1 | 1 分钟后 | ← 本轮之内 |
| 2 | 5 分钟后 | ← 本轮之内 |
| 3 | 15 分钟后 | ← 本轮之内 |
| 4 | 1 天后 | |
| 5 | 2 天后 | |
| 6 | 4 天后 | |
| 7 | 7 天后 | |
| 8 | **15 天后** | ← 到这一档算「已掌握」 |
| 9 | 30 天后 | |
| 10 | 60 天后 | |
| 11 及以后 | 120 天后（约 4 个月） | |

**为什么前三档要精确到分钟**：艾宾浩斯曲线的特点就是「刚记完忘得最快」。
新词必须在**一次学习之内**反复碰几次，把第一波遗忘压住；拖到第二天再见，等于白白多忘一轮。

**为什么前三档是 1 / 5 / 15 分钟，而不是 5 分钟 / 30 分钟 / 12 小时**：
因为人的一次学习通常只有十几分钟。如果档位长到「30 分钟」「12 小时」，
它们根本落不到你实际的学习时段里，只会变成「明天再见」—— 档位够得着才有意义。

### ⚠️ 「本轮之内重新排队」——这条不做，前几档就是摆设

前三档只有几分钟，可背单词页在打开时就把这一轮的词取好了，队列是固定的。
**如果什么都不做，一个被排到「5 分钟后」的词在本轮里永远不会再出现**，
只能等下次打开网站 —— 那时它早就逾期了。

所以：**间隔短于 30 分钟的词，会被重新塞回本轮队列末尾，当场再考你一次。**
点完按钮后你会看到提示「（本轮还会再考一次）」。

同一轮里每个词最多重排 3 次（否则一直点「不认识」会让这一轮结束不了）。

### 三个按钮的作用

| 你的选择 | 复习间隔 | 星级熟练度 |
| --- | --- | --- |
| **认识** | 往上走一档（间隔变长） | **+1 颗** |
| **模糊** | 往下退**一档**（不会一次打回原点） | **不变** |
| **不认识** | 归零，1 分钟后重来 | **−1 颗** |

### 星级熟练度（0 ~ 5 颗）

每个词一开始都是 **3 颗星** —— 刚见到它的时候，本来就无从判断会不会：

```
★★★☆☆  3 颗   新词起步
★★★★☆  4 颗   答对一次
★★★★★  5 颗   答对两次（到顶）
★☆☆☆☆  1 颗   连错两次
☆☆☆☆☆  0 颗   连错三次（到底）
```

- 范围 **0 ~ 5 颗**：到顶就不再涨，到底也不会变成负数
- 点「模糊」既不涨也不掉
- 背单词时，按钮下面会实时显示这个词作答后的星级

> **实现上的一个好处：星级不需要单独存一列。**
> 因为「模糊」两边都不计数，所以
> `星级 = 3 + 答对次数 − 答错次数`（再截断到 0~5）
> 正好等价于上面这套加减法。这两个计数数据库里本来就有 ——
> **不用改表结构，也不用迁移历史数据。**

> 注意区分：首页的「已掌握」统计**仍然按艾宾浩斯阶梯算**
> （间隔排到 15 天以上才算），不是「5 颗星」。
> 因为点两次认识就能到 5 颗星，用它当「已掌握」太容易了。
> 星级反映的是**最近的手感**，阶梯反映的是**长期记忆**。

规则在 `lib/spaced-repetition.ts` 的 `calculateStars()`。
这个文件（算法 + 星级 + 本轮重排）共 39 个测试盯着，改完跑 `npm test` 即可确认没改坏。

## 重点词（根据掌握情况挑出来的）

首页和 `/focus` 页面会列出**最该盯的词**。它和「今日待复习」不是一回事：

- **今日待复习**：艾宾浩斯时间表说到期了，该看了
- **重点词**：不管到期没到期，从你的**错误记录**看它就是个隐患

一个还没到期、但你连着错了三次的词，才是真该盯的。

### 评分依据

| 信号 | 权重 |
| --- | --- |
| 掌握程度 | 不认识 +50 · 模糊 +30 · 认识 +8 · 已掌握 +0 |
| 错误率 | 最多 +25 |
| 累计答错次数 | 每次 +4，最多 +20 |
| 逾期天数 | 每天 +2，最多 +30 |
| 最近一次没答对 | +10 |

综合评分低于 10 的不会出现在列表里（避免把背熟的词也塞进来）。
每个词下面都会写明**它为什么被挑中**（例如「总是模糊」「错误率 75%」「已逾期 3 天」），
让你自己判断该不该多花时间。

判定逻辑在 `lib/focus.ts`（15 个测试盯着）。点「马上攻克这些词」会进入
`/study?focus=1` —— 只背重点词，不管到没到期。

## 数据安全原则

1. 核心学习进度**存在 Supabase 数据库**，不只放在浏览器 localStorage 里。
2. 每个用户只能读写自己的学习记录 —— 靠 RLS 在**数据库层**强制保证，而不是靠前端代码自觉。就算有人改了浏览器里的代码，数据库依然会拒绝。
3. 登录凭证存在 HttpOnly cookie 里，浏览器上的 JavaScript 读不到，防 XSS 窃取。
4. API Key、数据库密钥写在 `.env.local`，这个文件不会提交到 Git。AI 接口一律在服务器端调用，密钥不进浏览器。
